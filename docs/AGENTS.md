# 专家公会与协作协议

48 位虚拟专家分三层，每次任务由调度器挑一个小队上场。
这份文档讲三件事：**名册怎么构成**、**队伍怎么选**、**专家之间怎么传话**。

---

## 为什么是"专家"，而不是"一个更长的提示词"

一个直接的问题是：既然最后都是一次 LLM 调用，为什么要把它叫成 48 个专家？

因为这个抽象**改变了两件事，而且两件都是可验证的**：

1. **提示词的内容不同。** 一个"AI 编程工具行业专家"的提示词里带着这个
   行业的分析框架（版本节奏、IDE 集成深度、模型成本转嫁），
   而一个通用提示词里没有。这不是装饰——它决定了模型去搜什么、
   把什么看成重要信号。
2. **团队构成是一个可观测的中间产物。** 报告里能回答"这次调研派了谁、
   为什么是他们"，而"一次 9000 token 的巨型调用"回答不了这个问题。
   决策回放要画的那张图，前提是消息有发送方和接收方。

这也意味着**名册是内容资产的一部分**。48 条 `experts_seed.yaml` 里
每一条的 `skills` 与 `knowledge_tags` 都是要写对行业才有用的东西，
而不是可以程序化生成的占位符。

## 名册构成

| 层级 | 人数 | 分组 | 职责 |
|---|---|---|---|
| **L3 决策层** | 3 | 决策 | 决定研究边界与最终取舍 |
| **L2 战略层** | 9 | 战略 | 各自从一条战略维度切进去 |
| **L1 执行层** | 36 | 行业 24 + 职能 12 | 行业与职能专才，负责取证 |

### L3 · 决策层（3 人）

| id | 姓名 | 角色 |
|---|---|---|
| `L3-001` | 沈衡 | 调研总监 |
| `L3-002` | 陆远 | 首席分析官 |
| `L3-003` | 纪岚 | 质检总监 |

### L2 · 战略层（9 人）

`L2-001` 竞争战略 · `L2-002` 定价与商业模式 · `L2-003` 用户研究 ·
`L2-004` 技术架构 · `L2-005` 增长与获客 · `L2-006` 渠道与生态 ·
`L2-007` 品牌与传播 · `L2-008` 供应链与交付 · `L2-009` 财务与资本市场。

九条维度是刻意选的：它们覆盖了一家公司在竞争分析里被问到的九个方向，
而且彼此有重叠区（渠道与生态 vs 品牌与传播），所以调研时会有交叉印证
的余地，而不是九条互不相干的线。

### L1 · 执行层（36 人）

**行业专家 24 人**（`L1-001`–`L1-024`）：AI 编程工具、知识管理、
新能源汽车、跨境电商、企业协同、云计算、智能手机、智能家居、
电商平台、本地生活、在线教育、短视频与直播、游戏、金融科技、
企业服务、数据库与中间件、信息安全、医疗健康、物流与供应链、
出行与网约车、芯片与半导体、机器人、消费电子、企业出海。

**职能专家 12 人**（`L1-025`–`L1-036`）：舆情分析、数据采集、
财报解读、渠道与价格监测、专利与技术情报、招聘信号、合规与法律、
数据可视化、数据质量校验、用户评论挖掘、竞品档案管理、海外情报。

行业与职能是两种不同的东西：行业专家提供**领域判断**
（"这个行业的定价通常怎么走"），职能专家提供**证据技能**
（"这份财报里该看哪一行"）。一份报告同时需要两种。

### 名册为什么是"手写 seed + 程序生成"而不是直接手写 48 条 JSON

`experts_seed.yaml` 是手写的语义内核（约 8 行/人）：
`id / level / group / name / role_title / one_liner / skills /
knowledge_base / knowledge_tags`。**每一条都是面试里讲得出的内容。**

`gen_experts.py` 生成机械字段：`avatarColor`、`badgeColor`（`hash(id) % palette`
稳定取色）、`domainIcon`（按 group 查表）、`stats` 初值。

直接手写 48 条 JSON 是 1500+ 行复制粘贴——语义对了，但会引入错别字、
重复 id、以及"改了 YAML 忘了改 JSON"的漂移。拆成两半之后，
手写的部分可以一口气审完，机械的部分由程序保证一致。

**"生成而非手写"要成立，得有一条测试证明它是幂等的**：
`test_experts.py` 里"重复生成字节一致"那条钉住了这一点。
没有它的话，"生成"和"随机"在结果上无法区分。

名册不变量由 `tests/unit/test_experts.py` 守护（46 条用例）：
恰好 48 人、id 唯一且匹配 `^L[123]-\d{3}$`、分布 3/9/24/12、
level 与 group 一致、无空必填字段、每人 `knowledge_tags` ≥ 3、
`one_liner` ≤ 40 字、生成幂等。

## 组队：两道关，不只是"id 存在"

调度阶段（`intake → orchestrator`）同时做两件事：**组队**和**定维度**。
它们被放在一个阶段里，是因为它们本来就是一个判断的两面——
"这次调研需要什么专业视角"和"要调研哪些维度"在真实项目里是同一个
决定的产物。分开会让模型在两次调用之间失去彼此的信息。

### 队伍的形状

```python
_ROLE_SPECS = (
    ("lead",        "L3", 1, (...)),   # 组长，恰好 1 人
    ("strategists", "L2", 3, (...)),   # 战略层，最多 3 人
    ("executors",   "L1", 4, (...)),   # 执行层，最多 4 人
)
```

上限存在是因为**人多不等于分析好**：每位专家都要在提示词里占位置，
人多会把真正需要的材料挤掉。

### 第一道关：id 得在名册里

模型很自然地会写出一个不存在的号。不校验的话它会一路走进
`expert_stats` 表，污染"每位专家参与了多少任务"，而且**没有任何地方
会报错**——统计页上的数字看起来完全正常，只是有一行属于一个
不存在的专家。

所以流程是：逐个 id 查名册 → 查不到的丢掉并记录 → 某一类全部丢掉时
用确定性默认队伍补上。

**绝不因为一次调度失败就让整个任务失败。** 用默认队伍跑出来的报告，
比一个"调度失败"的错误页有用得多。

这里踩过一个真实的坑：名册是 `- L3-002 首席分析官` 这个形状喂进去的，
而模型很自然地**把整行抄回来**，于是 `lead` 字段收到的是
`"L3-002 首席分析官"` 而不是 `"L3-002"`。原先拿整串去查字典，
查不到就记进 `phantom`——而 `phantom` 的语义是"模型在编 id"。

结果是：**校验器把一个真实存在的人报成了不存在**，观测通道说了假话，
并且三个角色全类回退默认队伍——48 人动态组队这个核心能力，
在 6 条真实调度响应里有 4 条根本没生效，而报告里那句话读起来
像是模型的错。

修法是 `_extract_id()`：先精确匹配，否则从文本里取出第一个 id 形状的
片段。**这段代码是照着录制下来的真实响应写的，不是照着想象中模型
该有的输出格式写的**，那 6 条响应现在有一条测试直接读它们。

### 第二道关：层级得对

id 存在还不够。48 人名册里有 36 个执行层，"号是真的但人被放错了层"
因此比"号是编的"**更常见**——一个战略层的人被指派成组长，在数据上
和一次正常调度长得一模一样。`_ROLE_SPECS` 里的层级要求是第二道关。

这一条原先也漏了，那是一个真的漏洞：校验只查"这个 id 在不在名册里"，
不查"它在哪一层"。名册从 15 人扩到 48 人之后，这个漏洞只会更容易
被踩到——"模型挑了个执行层当组长"从一个边角情况变成了一件常事。

### 四类问题分开记，不合成一个数

`TeamOutcome` 把调度问题分成四类：

| 字段 | 含义 | 这是谁的错 |
|---|---|---|
| `phantom` | 名册里查不到的 id | **模型的错**，它在编 |
| `wrong_level` | id 存在但层级不对 | 模型的错，它没读层级要求 |
| `over_limit` | 合法但超出上限被截掉 | **我们的取舍** |
| `fallback_roles` | 整类回退到默认队伍 | 调度没生效 |

原先这四种被合成描述成"N 个专家 id 不存在于名册"——而其中只有第一种
是真的不存在。实测那次报告里的"有 11 个专家 id 不存在于名册"，
里面就混着后两种。

> **观测通道说的每一句话都必须是真的**，否则"全程可观测"这条铁律
> 就只剩一个好看的界面。所以这里宁可多几个字段，也不把四类压成一个数。

## 消息协议：Envelope

专家之间传递的消息：

```python
@dataclass
class Envelope:
    sender: str
    recipient: str
    kind: Literal["request", "result", "issue", "handoff"] = "result"
    payload: dict = field(default_factory=dict)
    trace_id: str = ""
    created_at: str = ""
```

四种 `kind`：

| kind | 方向 | 含义 |
|---|---|---|
| `request` | 决策层 → 执行层 | 派活 |
| `result` | 执行层 → 决策层 | 交回结果 |
| `issue` | 质检总监 → 任意层 | 打回，附 Issue |
| `handoff` | 同层之间 | 交接（"这块归你"） |

**刻意保留 `sender` / `recipient`，而不只是内容**：三层专家分工的
可解释性依赖于"谁把什么交给了谁"，决策回放要画的就是这张图。
一个只有内容的信封能渲染出一段文字，但画不出一张有向图。

## 质检协议：Issue

一条质检问题，与"日志里的一行警告"的区别是：

```python
@dataclass
class Issue:
    issue_id: str
    kind: str
    severity: Severity = "minor"          # blocker / major / minor
    dimension: str = ""
    brand: str = ""
    detail: str = ""
    suggestion: str = ""                  # ← 该怎么办
    targets: list[str] = field(...)       # ← 返工时要补的搜索角度
    evidence_ids: list[str] = field(...)
    resolved: bool = False
```

**`suggestion` 与 `targets` 是它存在的理由。** 有了它们，Issue 可以
驱动一次具体的返工——补采哪个维度的哪些 query。没有的话，
问题清单就只是一份抱怨。

`ISSUE_KINDS` 里 9 种问题，**每一种都对应一条明确的返工动作**：

| kind | 含义 |
|---|---|
| `thin_evidence` | 某个维度的证据密度不足 |
| `missing_dimension` | 计划里的维度完全没有证据 |
| `uncited_claim` | 论点没有可核验的证据引用 |
| `single_source` | 论点只有一个独立信源，未通过交叉验证 |
| `low_credibility` | 该维度证据平均可信度过低 |
| `phantom_citation` | 论点引用了不存在的证据 |
| `stale_evidence` | 该维度证据过于陈旧 |
| `empty_section` | 章节没有实质内容 |
| `degraded_source` | 该维度证据以抓取失败后的摘要为主 |

`issue_id` 由 `kind + 维度 + 品牌 + detail` 摘要生成——
**同一轮里重复发现的问题不会被记成两条**。

只有 `severity == "blocker"` 的 Issue 才阻塞交付（`is_blocking`）。

## 四条铁律

这四条贯穿全部设计，改动时不要破坏。

### 一、无证据不立论

每个论点必须挂到具体证据上。实现位置
[`core/evidence/citations.py`](../backend/app/core/evidence/citations.py)
的 `enforce_citations()`。

关键在于**校验依据的是实际存在的证据，不是模型的自我陈述**：

```python
#: 下面两个字段由 evidence/citations.py 依据**实际存在的证据**计算，
#: 不采信模型的自我陈述。模型说"我引用了 3 条"和这 3 条真的存在是两回事。
verified: bool = False
cross_validated: bool = False
phantom_evidence_ids: list[str] = field(default_factory=list)
```

模型编造的引用被丢弃并计数，这个数就是**幻觉引用率**的分子。

铁律一还管到图表：`analysis/charts.py` 的出口处有一道收口——
**没有证据链的图一律不生成**，并记一条降级。图表也是论点。

### 二、交叉验证

高置信结论需要 ≥2 个独立域名支撑。`cross_validate()` +
`sourcetypes.independent_domain()`。

难点在"独立"怎么算。同一篇文章被 5 家门户转载，是 5 个信源还是 1 个？
所以 `sourcetypes.py` 里有一张平台归属表：同一个内容平台下的站点
共享编辑立场与同一批信源，不能互相印证。

`MIN_INDEPENDENT_DOMAINS = 2`。这个常量有一条注释说明它是铁律的原文，
**降到 1 等于取消这条铁律**。

### 三、返工闭环

质量不达标就打回重做，不降低标准。

`audit` 阶段产出 Issue 列表 → `decide_rework()` 判断是否返工 →
返工后 `metrics_after - metrics_before` 就是这条铁律**唯一可量化的证据**
（`analysis/metrics.py`）。没有这个差值，"返工有效"就只是一句话。

### 四、全程可观测

每次调用的输入输出、耗时、成本、决策依据都可回放。

实现是 contextvars 无侵入埋点：阶段代码不需要手动传 tracer，
`call` 的包装器自动捕获。`observability/` 包提供两条独立的东西——
span 树（给人看）与事件 journal（给前端推）。

**这条铁律约束的是观测通道本身的诚实度**，不只是"有没有埋点"。
`dispatch.py` 里那段"四类问题分开记"的注释就是这条约束的体现。

---

## 一句话总结

48 个专家不是 48 个提示词，而是**一个把"这次调研派了谁、交了什么东西、
哪里没过关"变成可观测数据**的结构。三条铁律各有一条测试或一个指标
盯着它是否真的在执行，第四条要求前三条的观测数据本身必须是真的。
